## 2. 근거

1. **원본 zip 안에서 이미 동일**: 쌍을 이루는 두 SEG-Y는 서로 다른 zip 멤버 경로(`09/09.5/Radargrams/Path7.sgy` 대 `Path12.sgy`, `03/03.5/...` 대 `03/03.6/...` 등)이지만 CRC32·SHA-256이 같다(38쌍). 변환 스크립트(`06_scripts/build_4tu_package.py`)는 멤버를 하나씩 읽어 파일 하나로 내보내므로 변환이 서로 다른 입력을 같게 만들 수 없다. 입력이 이미 같다.
2. **취득 시각 동일**: 모든 쌍에서 첫 트레이스 헤더의 연·일·시·분·초(바이트 157–166, little-endian)가 같다(불일치 0). 복사된 파일이지 같은 장소를 두 번 잰 것이 아니다(두 번 쟀다면 트레이스 값이 비트 단위로 같을 수 없다).
3. **조건 메타가 서로 모순**: 같은 측정이 두 활동에 있는데 활동 조건이 다르다(`Metadata.csv`·`activities_metadata_ko.csv`). 예: 03.5 날씨 비 / 03.6 건조(관로 수 메타 19 / 7), 010.11 보도·010.12 차도·자전거도로, 02.2 콘크리트 포장·보도 / 02.4 잔디·녹지, 012.2 잔디·녹지 / 012.4 블록 포장·차도. 정답표 행 수도 다르다(아래 §3). 한 번의 측정이 둘 모두에 속할 수 없으므로 최소 한쪽의 레이더그램 배정이 틀렸거나, 측선 세트를 활동 폴더에 통째로 복사해 둔 것이다. 정답표·측선 배치도 png는 쌍마다 서로 다르다(해시 다름).
4. **09.5 활동 안 사본**: Path12–16은 Path7–11과 시각·데이터가 같고 zip 멤버 수정 시각만 98초 뒤다(Path7–11: 2020-04-03 12:56:34, Path12–16: 12:58:12). 측선 번호가 Path17까지 이어지고 Path17의 취득 시각은 활동 맨 처음(12:33:02)이라서 번호 순서와 시각 순서도 일치하지 않는다. 원본 제공자가 파일을 다시 복사한 흔적이다. Path8/Path13의 텍스트 헤더만 40행(바이너리 꼬리)이 다른 것도 같은 맥락이며 트레이스 값은 같다.
5. **03.5/03.6 세트 복제**: 03.6은 Path1–10이 03.5와 같고 Path11–13(13:18:12–13:19:49)이 03.6에만 있다. 03.6이 03.5 세션 전체에 이어진 것을 담고 있어 03.6 쪽이 상위 집합이다. 어느 쪽이 실제 측정이 속한 활동인지는 시각만으로 확정되지 않는다.
6. **경계 2쌍(i-c)**: 012.2 Path1–6은 11:40:50–11:45:10(약 52초 간격), Path7이 11:46:06, 012.4 Path2가 11:47:11이다. 09.6은 Path4 08:06:15, Path2 08:12:56, Path3 08:18:54이고 공유 Path1이 08:36:29이며 09.7의 나머지는 09:12:50 이후다. 시각 간격만으로는 두 활동 모두 가능하다(09.6 쪽이 약간 가깝다). **판단 불가**.
7. 서버 원본(4TU.ResearchData)의 해시와는 오프라인이라 대조하지 못했다. `00_원본`이 서버에서 받은 그대로라는 가정(가공본 README: "원본 그대로")이다.

## 3. 활동별 정답 행 수(값은 보지 않음)와 메타 차이

정답표 행 수만 집계했다. 두 활동의 행 수가 같아도 값이 같은지는 확인하지 않았다.

| 쌍 | 현장 | 복제 측선 / 각 활동 측선 수 | 정답 행 수 (앞/뒤) | 조건 메타 차이(요약) |
|---|---|---|---|---|
| 010.11 = 010.12 | 10 | 10 / 10, 10 | 7 / 14 | 지표 유형(보도 / 차도), 지하수위, 관로 수 메타 2 / 14 |
| 010.15 = 010.16 | 10 | 1 / 1, 1 | 3 / 2 | 관로 수 3 / 2 |
| 012.2 = 012.4 | 12 | 1 / 7, 2 | 2 / 1 | 지표 피복·유형, 관로 수 메타 4 / 1, 교차 관로, 관종 목록 |
| 013.1 = 013.2 | 13 | 3 / 3, 3 | 2 / 2 | 관종 목록만(U\|U / OGC\|E) |
| 02.2 = 02.4 | 2 | 8 / 8, 8 | 0 / 0 | 지표 피복·유형, 관로 수 메타 2 / 6 |
| 03.5 = 03.6 | 3 | 10 / 10, 13 | 7 / 6 | 날씨(비 / 건조), 관로 수 메타 19 / 7 |
| 09.6 = 09.7 | 9 | 1 / 4, 9 | 0 / 0 | 지표 피복·유형, 관로 수 메타 6 / 0 |
| 09.5 (활동 안) | 9 | 5 / 16 | 0 | - |

정답 행이 있는 중복 활동 쌍은 5개(010.11/12, 010.15/16, 012.2/012.4, 013.1/2, 03.5/03.6)이고 두 활동의 정답 행을 모두 합하면 7+14+3+2+2+1+2+2+7+6 = 46행이다. 이 활동들의 같은 B-scan이 서로 다른(대부분 행 수가 다른) 정답 집합에 대해 두 번 평가되거나 한쪽이 틀린 정답 집합과 매칭된다. 02.2/02.4와 09.x 쌍은 정답 행이 없어 깊이 평가에는 영향이 없고 측선 수 통계(`n_lines` 지지 필터)에만 영향이 있다.

## 4. 처리 규칙 추천

> **채택 규칙(2026-11-07 사용자 결정)은 [`spec_eval_4tu_v1.md`](../processing/spec_eval_4tu_v1.md) §4-5가 정본이다.** 아래는 결정 전 curator 추천이며 채택값과 다른 점: 단서 문턱은 5 %p가 아니라 **2 %p**, `keep_one`은 "측선 수"가 아니라 **엄격 상위 집합, 아니면 활동 번호 작은 쪽**(012.2는 상위 집합이 아니라 번호 규칙으로 남음).

분류가 전부 (i) 원 데이터셋 중복이라 "가공 오류로 고치면 되는" 경우는 없다. 정답이 활동 단위인 이상 어느 쪽이 맞는지 GT를 보지 않고 정할 수 없으므로 아래를 추천한다.

1. **활동 안 중복(09.5, i-a)**: 한 측선으로 센다. 번호가 작은 Path7–11을 대표로 두고 Path12–16에 `duplicate_radargram=within_activity`를 표시해 2선 지지 필터(`n_lines`)와 측선 수 통계에서 뺀다. 정답이 없는 활동이라 깊이 지표에는 영향이 없다.
2. **활동 사이 중복(i-b·i-c 34쌍)**: 주 결과는 **둘 다 유지 + `duplicate_radargram=across_activities` 표시**를 추천한다. 이유: (a) 어느 활동이 진짜 소속인지 시각·메타로 확정할 수 없다(03.5/03.6은 날씨 모순뿐), (b) GT를 보고 한쪽을 고르면 평가 독립성이 깨진다, (c) 한쪽을 임의로 빼면 그쪽 GT 행이 통째로 사라져 결과가 바뀐다.
3. **민감도 분석(필수 병기)**: 사전 규칙(GT 비의존)으로 한쪽 제외 결과를 함께 낸다. 규칙: 측선 상위 집합이 있으면 그쪽을 남기고(03.6, 12.2는 7선 보유로 012.2), 같으면 활동 번호가 작은 쪽을 남긴다(010.11, 010.15, 013.1, 02.2, 09.6). 보조로 중복 측선이 있는 활동을 전부 뺀 결과도 한 줄 낸다. 세 결과의 MAE·판정률 차이가 크면(예: 5 %p 이상) 주 결과에 단서를 단다.
4. 집계 단위는 현장(site) 13개로 유지한다. 중복 쌍은 모두 같은 현장 안에 있어 현장 수는 변하지 않지만, 중복 때문에 가중이 늘어난 현장(10, 3, 2, 13)의 가중은 민감도 분석에서 확인한다.
5. 4TU 재평가 1회 원칙: 위 규칙은 GT를 보지 않고 정했으므로 지금 확정해도 된다.

## 5. 한계

- 비트 단위 동일한 중복만 찾았다. 게인이 다른 사본, 시간 방향 부분 자르기, 속도 보정본 같은 변형 중복은 비공백 트레이스 해시 오프라인 정렬(0건)과 뒤집기(0건)만 확인했고, 상관 기반 유사도는 보지 않았다.
- 서버 원본(4TU.ResearchData)과 `00_원본` zip의 해시 대조는 오프라인이라 못 했다.
- 어느 활동이 진짜 소속인지는 정답표를 읽어야 판단되는데, 재평가 1회 원칙 때문에 읽지 않았다.
